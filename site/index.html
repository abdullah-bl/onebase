Live queries

Every client stays up to date. You don't write any sync code.

Clients subscribe to queries. When a mutation commits, onebase re-runs only the queries whose data changed and pushes the new results over WebSocket. Try it:

      Write the backend in TypeScript

      A schema, some functions, and a hook. That's the whole backend.

      The API follows Convex: query, mutation, action, v.* validators, ctx.db. Everything is typed, from the schema to the React component.

      onebase/messages.tsserver
      import { v } from "onebase/values";
import { mutation, query } from "./_generated/server";

export const list = query({
  args: { channel: v.id("channels") },
  handler: (ctx, { channel }) =>
    ctx.db
      .query("messages")
      .withIndex("by_channel", (q) => q.eq("channel", channel))
      .collect(),
});

export const send = mutation({
  args: { channel: v.id("channels"), body: v.string() },
  handler: async (ctx, args) => {
    const user = await ctx.auth.getUserIdentity();
    const author = user?.name ?? "anonymous";
    return ctx.db.insert("messages", { ...args, author });
  },
});
      app/Chat.tsxclient
      import { useMutation, useQuery } from "onebase/react";
import { api } from "../onebase/_generated/api";

export function Chat({ channel }) {
  // Re-renders whenever anyone sends a message.
  const messages = useQuery(api.messages.list, { channel });
  const send = useMutation(api.messages.send);

  return (
    <>
      {messages?.map((m) => (
        <p key={m._id}><b>{m.author}</b> {m.body}</p>
      ))}
      <button onClick={() => send({ channel, body: "hi" })}>
        Say hi
      </button>
    </>
  );
}
      Batteries included

      The parts every app ends up needing.

      Fine-grained live queries

      A new message in channel A never re-runs the query for channel B. Identical subscriptions share a single execution.

      Real transactions

      Mutations are atomic and serializable. Throw an error and none of the writes happen, even across several servers.

      Node and npm everywhere

      Every function runs in Bun. Import any package from a query, a mutation or an action. There's no "use node".

      Typed end to end

      The types flow from the schema to ctx.db, to api.*, to useQuery. Arguments are validated at runtime too.

      Scheduler and crons

      runAfter, runAt and cron jobs survive restarts. Each run happens exactly once, even with several instances.

      File storage

      Uploads stream to disk or to S3, R2 or MinIO, so big files never sit in memory. Downloads come from presigned URLs.

      Auth that plugs in

      Clerk, Auth0, WorkOS or any OIDC issuer, in the same config format as Convex. Tokens are verified with WebCrypto.

      SQLite, Postgres or Turso

      Start on SQLite. Switch with --db when you need more servers, and your functions don't change.

      Backups to S3

      Consistent SQLite snapshots, gzipped and uploaded on a schedule. onebase restore brings them back.

      Hard to get wrong

      Made for code written by people and by LLMs.

      The API is the one models already know from Convex. It forgives the usual mistakes, and when something is wrong it says how to fix it.

      • .filter({ done: false }) works, and it uses an index when one exists.
      • Every error names the problem and the fix: the wrong field, a missing index, an argument that doesn't match.
      • onebase doctor checks a project in one command, and the docs come as llms-full.txt to give your assistant.
      $ onebase doctor

      Deploy

      From a $5 VPS to a fleet of servers.

      One binary. Pick the database that fits your setup today, and change it later without touching your functions.

      one server

      SQLite + S3 backups

      The default. Reads take microseconds, there's no database to run, and hourly snapshots go to any S3-compatible storage.

      onebase serve \
  --backup s3://bucket/backups
      many servers

      Postgres

      Run as many instances as you need behind a load balancer. Live queries are shared through LISTEN/NOTIFY, and mutations are serializable.

      onebase serve \
  --db postgres://…/app \
  --files s3://bucket/files
      managed SQLite

      Turso

      SQLite semantics without running a database yourself, and still as many instances as you like.

      TURSO_AUTH_TOKEN=… onebase serve \
  --db libsql://my-db.turso.io
